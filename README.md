本文记录一次本地 WebViewer 内核修改的内容、前后性能测试与功能验证范围。记录日期：2026-10-07。

## 1. 修改了什么

最后一次成功部署仅替换了一个安装文件：

```text
core/pdf/lean/PDFNetThreadedWasm.br.wasm
```

它是 Brotli 压缩的 WebAssembly 二进制，属于原有 Apryse/PDFTron WebViewer 的 lean 多线程内核。该修改沿用原阅读器和 PDF 引擎。

这份特定构建中，有两个原始函数的页面叠加绘制分支被修改，涉及 `f3284` 和 `f13914`；原先的检查调用仍执行，但这两处后续目标绘制分支不再进入。另外增加了 9 个诊断全局量及导出，用于记录实验版本和本实例计数。函数编号只对应本次核对的二进制版本，不是稳定公开 API。

最终构建仅改变 WASM 的 globals、exports、code 三个 section，两个原始函数体发生变化。此前引发读取权限异常的共同检查函数 `f7851` 的改动没有保留。配套 `.br.mem` 文件、图形轮廓数据、插件 UI、Pro 笔记适配代码没有随这次最终部署修改。

实测效果是：本机 Obsidian 加载这份修改后的 lean 多线程内核，测试 PDF 能正常显示，页面上的 PDFTRON 叠加水印消失，使用者随后确认成功。这个结果不等于已经验证打印、下载、其他内核或所有 PDF。

“最后一次替换一个文件”仅描述最终成功部署。早期实验曾修改其他普通内核文件和加载器，不能据此声称整个安装目录只改过一个文件。性能对照时，除目标 WASM 响应外，其余资源在两组间完全相同。

## 2. 性能提升还是降低

**本轮实测：首屏接近但略慢，后续画布渲染更快，压缩包体增加。不能由这组结果断言整个 WebViewer 或 Obsidian 全面提速。**

以下为各 10 次测量的中位数。耗时越低越好；百分比是修改版相对原版的变化。

| 项目 | 修改前 | 修改后 | 变化 |
| --- | ---: | ---: | ---: |
| WASM 压缩体积 | 1,928,136 字节 | 2,306,183 字节 | +19.61% |
| WASM 解压体积 | 8,562,811 字节 | 8,563,197 字节 | +386 字节 |
| 文档加载事件 documentLoaded | 557.75 ms | 575.20 ms | 耗时 +3.13% |
| 首屏完成事件 pageComplete | 751.00 ms | 757.85 ms | 耗时 +0.91% |
| 后续 6 次画布渲染总耗时 | 109.50 ms | 97.35 ms | 耗时 −11.10% |

首屏中间 50% 的样本区间：原版 740.72–758.35 ms，修改版 752.40–764.75 ms。区间重叠，不能把约 7 ms 的中位数差异解释成稳定的整体退化；本次没有做统计显著性检验。六次渲染总耗时对应区间为 108.95–113.65 ms 与 93.35–99.87 ms。

压缩体积增加主要与本次重新 Brotli 压缩的设置有关，构建使用 quality=6。解压后的模块只增加 386 字节，不能把压缩包体增加 19.61% 写成执行代码增加或运行变慢 19.61%。本地与网络加载、冷缓存与热缓存的结果也不能直接互换。

### 测试方法和限制

| 项目 | 设置 |
| --- | --- |
| 系统 | Windows 11 x64，系统版本 10.0.22631 |
| 硬件 | i9-13900HX，32 个逻辑处理器，约 32 GiB 内存 |
| 软件 | Edge 154.0.4258.53，无头模式；Node.js 22.21.1 |
| 测试 PDF | 自行生成的 4 页简单文本，每页 600 × 800 点 |
| 内核 | 启用 SharedArrayBuffer，每轮验证实际请求为 lean 多线程 WASM |
| 对照变量 | 只替换该 WASM 的 HTTP 响应，配套内存文件和其他资源相同 |
| 轮次 | 两组各预热 1 次；再按 A B B A 重复 5 组，两组各计 10 次 |
| 缓存 | 每轮新浏览器上下文，HTTP no-store；浏览器进程、操作系统缓存未重置 |
| 首屏计时 | 页面导航起点至第 1 页 pageComplete 回调 |
| 渲染计时 | 第 2、3、4 页按缩放 1、1.5 依次绘制，共 6 次 loadCanvasAsync，总计回调等待耗时 |

全部 22 轮，包括预热，都完成了指定页面加载与渲染，未捕获到 pageerror。逐轮原始数据、环境和统计结果见 [performance-results.json](reports/performance-results.json)。额外的 Node.js Brotli 解压微基准也保留在 JSON 内，但不能代表浏览器内完整加载耗时。

这是独立 Edge 中的 WebViewer 对照测试，不是完整 Obsidian 基准。未测量大型扫描件、复杂矢量图、全书滚动帧率、CPU/GPU 占用、峰值内存、打印速度或长时间稳定性。减少一部分绘制工作与渲染耗时下降相符，但本次没有通过性能剖析把全部差异归因到某条指令。

## 3. 是否影响其他功能

**已测路径未观察到异常；不能承诺所有功能不受影响。**

| 项目 | 已有证据与范围 |
| --- | --- |
| 实际 Obsidian 加载 | 模块实验版本为 3，PDF 正常打开，使用者确认页面效果 |
| 合成 PDF 内容 | 原版与修改版像素对照中，顶部 150 像素的文本区域变化为 0 |
| 页面绘制与不同缩放 | 本轮两组各 10 次正式测量，指定 6 次画布渲染均完成 |
| 已有标注 | 修改前后均读取到 653 条；仅核对 Id、PageNumber、X、Y、Width、Height、Subject，一致 |
| 待保存队列 | 最终现场记录为 0，界面显示“可编辑 · 自动保存到 Pro”；这不等于重新测试了全部写回操作 |
| 未充分回归 | 新增、移动、删除标注，图片和链接读写，打印、导出、加密 PDF、多窗口、长时间运行 |

未改动插件的笔记适配层是修改范围事实，不是这些功能绝对不受底层影响的证明。完整标注文本、颜色、图片字节、附件和 Pro 数据库没有在本轮逐字节对照。

## 4. 此前错误与最终成功的原因

早期有几类证据不足的判断，造成了反复试错：

1. 找到 `PDFTRON` 文本常量，就推断它直接控制可见水印；修改后像素差异为 0，否定了这个候选。
2. 在独立绘制输出中得到 `PDFTRON!`，便把它扩大成实际 Obsidian 页面也已改变；两者的加载路径和绘制时机不同。
3. 没有先固定 full/lean、普通/多线程内核，部分修改没有落到实际使用的文件。
4. 把一个候选绘制入口当成唯一入口；后来实际调用栈显示还存在此前遗漏的路径。
5. 修改共同权限判断，导致 PDF 无法读取；这个失败方案随后撤销。
6. 多次把文件复制成功、静态代码推断或隔离测试成功，提前当成用户现场已成功。

最终先核对实际加载的 lean 多线程文件，再处理两个已定位绘制分支，并通过隔离像素对照、安装文件哈希、实际运行模块标识、Obsidian 页面和用户确认建立对应证据。该组合成功，但没有做单独移除其中一处的对照，因此不能断言两处缺一不可。
